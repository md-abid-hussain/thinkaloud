Stage 0 · understand the problem

You will build a command-line tool that counts the bytes, lines, words and characters in a text file, and that gives the same answers as the Unix wc tool. The input is either a file named on the command line or text piped in from another program, and the output is a set of counts printed to the terminal. The tool looks simple, but each count has a precise meaning: a line ends at a newline, a word is a run of non-whitespace, and a character depends on the text encoding and the locale. The hard part is getting those meanings exactly right while reading input that may be larger than the computer's memory, in one pass that can't be rewound.

p-whatwhat

A user runs the tool on a text file and also pipes text into it from another program. What does the tool take in, what does it give back, and what does a word mean here?

  • It takes a file name or standard input, and gives back counts printed to the terminal
  • A word is a run of characters separated by whitespace, not a single space-separated piece
  • Lines are counted by newline characters, so the last line without a newline may not count
p-whywhy

Why would someone need a small tool that only counts lines, words and bytes, when editors and spreadsheets exist? Think about where it would show up in daily work.

  • Quick checks on the size or shape of data without opening it in an editor
  • Used in scripts and pipelines, where one tool's output feeds the next
  • Small, single-purpose tools can be chained together to do bigger jobs
p-howhow

A log file is far bigger than the computer's memory, so it can't be loaded whole. How would you approach counting its words without holding all of it at once?

  • Read the input in fixed-size pieces and reuse the same space each time
  • Keep running totals and update them as each piece arrives
  • Remember whether the last character was whitespace, since a word can be split across two pieces

Stage 0 · understand the problem

You will build a program that reads one file and decides whether it contains valid JSON, a text format for structured data that is widely used to send information between systems. It reports its verdict in two ways: a message a person can read, and a success or failure code that scripts and other tools can act on. The input is just text, so the program has to turn raw characters into meaningful pieces and then check how those pieces are arranged. What makes it harder than it looks is that 'looks right' is not the test: the format's written rules decide every case, including tricky ones like escaped characters, unusually written numbers and structures nested inside other structures. Read the format's definition before you write any code, because that definition is the only judge of what counts as valid.

p-whatwhat

The program is given one file and must answer whether it is valid. What does it take in and give back, and what decides whether the file counts as valid?

  • the input is a single file of text
  • the output is a readable message plus a success or failure code
  • valid means the text matches the format's grammar, not that it looks roughly right
p-whywhy

Where would someone use a program like this, and why would a team want one before the data is used? Think about data that comes from users or other systems.

  • data from users or other systems can't be trusted to be well formed
  • configuration files and API payloads are common places this check runs
  • checking early gives a clear error instead of a crash or wrong result later
  • a machine-readable result lets scripts and pipelines stop automatically
p-howhow

Before writing any code, how would you split the job of deciding whether a file is valid? Describe the first idea in plain words.

  • first group raw characters into meaningful pieces such as brackets, strings and numbers
  • then check the order of those pieces against the format's rules
  • begin with the simplest version that handles a small valid input and widen it from there

Stage 0 · understand the problem

You build a small web service, like the link shorteners people use to share long web addresses. A client sends in a long address and gets back a short code and the short address that contains it. Anyone who opens the short address should be sent on to the original page. The hard part is that each short code must always point to exactly one long address, the same long address should keep getting the same short link, and deleting a link has to really remove it. Because anyone on the internet can submit anything, the service also has to decide which input it accepts.

p-whatwhat

A client posts a long address to the service, opens a short one, and later asks to delete it. What does each of those requests promise the client, and what does the client get back?

  • posting a long address returns a short code, the long address and the short address, and posting it again returns the same link
  • opening a short address sends the visitor on to the original address
  • deleting removes the link, and asking to delete an unknown link still gets a clear answer
p-whywhy

Who calls this service, and what would those callers lose if it went down or started giving different answers for the same link?

  • other programs, scripts and people clicking links rely on it
  • a short link shared in a post or printed somewhere has to keep working for as long as people expect
  • a changed or missing answer breaks everyone who stored or repeated the short address
p-howhow

The service may restart at any time, and more than one copy of it may run at once. Where would you keep the short codes and their long addresses so they are not lost, and why?

  • keep them outside the running program, in a database or file, so a restart does not wipe them
  • a memory-only store works for a quick try but loses every link on restart
  • copies running side by side must all see the same data, so the store has to be shared
  • the store must find a link by its code quickly
