Stage 0 · understand the problem

You will build a command-line tool that counts the bytes, lines, words and characters in a text file, and that gives the same answers as the Unix wc tool. The input is either a file named on the command line or text piped in from another program, and the output is a set of counts printed to the terminal. The tool looks simple, but each count has a precise meaning: a line ends at a newline, a word is a run of non-whitespace, and a character depends on the text encoding and the locale. The hard part is getting those meanings exactly right while reading input that may be larger than the computer's memory, in one pass that can't be rewound.

p-whatwhat

A user runs the tool on a text file and also pipes text into it from another program. What does the tool take in, what does it give back, and what does a word mean here?

  • It takes a file name or standard input, and gives back counts printed to the terminal
  • A word is a run of characters separated by whitespace, not a single space-separated piece
  • Lines are counted by newline characters, so the last line without a newline may not count
p-whywhy

Why would someone need a small tool that only counts lines, words and bytes, when editors and spreadsheets exist? Think about where it would show up in daily work.

  • Quick checks on the size or shape of data without opening it in an editor
  • Used in scripts and pipelines, where one tool's output feeds the next
  • Small, single-purpose tools can be chained together to do bigger jobs
p-howhow

A log file is far bigger than the computer's memory, so it can't be loaded whole. How would you approach counting its words without holding all of it at once?

  • Read the input in fixed-size pieces and reuse the same space each time
  • Keep running totals and update them as each piece arrives
  • Remember whether the last character was whitespace, since a word can be split across two pieces

Stage 0 · understand the problem

You will build a program that reads one file and decides whether it contains valid JSON, a text format for structured data that is widely used to send information between systems. It reports its verdict in two ways: a message a person can read, and a success or failure code that scripts and other tools can act on. The input is just text, so the program has to turn raw characters into meaningful pieces and then check how those pieces are arranged. What makes it harder than it looks is that 'looks right' is not the test: the format's written rules decide every case, including tricky ones like escaped characters, unusually written numbers and structures nested inside other structures. Read the format's definition before you write any code, because that definition is the only judge of what counts as valid.

p-whatwhat

The program is given one file and must answer whether it is valid. What does it take in and give back, and what decides whether the file counts as valid?

  • the input is a single file of text
  • the output is a readable message plus a success or failure code
  • valid means the text matches the format's grammar, not that it looks roughly right
p-whywhy

Where would someone use a program like this, and why would a team want one before the data is used? Think about data that comes from users or other systems.

  • data from users or other systems can't be trusted to be well formed
  • configuration files and API payloads are common places this check runs
  • checking early gives a clear error instead of a crash or wrong result later
  • a machine-readable result lets scripts and pipelines stop automatically
p-howhow

Before writing any code, how would you split the job of deciding whether a file is valid? Describe the first idea in plain words.

  • first group raw characters into meaningful pieces such as brackets, strings and numbers
  • then check the order of those pieces against the format's rules
  • begin with the simplest version that handles a small valid input and widen it from there

Stage 0 · understand the problem

You build a small web service, like the link shorteners people use to share long web addresses. A client sends in a long address and gets back a short code and the short address that contains it. Anyone who opens the short address should be sent on to the original page. The hard part is that each short code must always point to exactly one long address, the same long address should keep getting the same short link, and deleting a link has to really remove it. Because anyone on the internet can submit anything, the service also has to decide which input it accepts.

p-whatwhat

A client posts a long address to the service, opens a short one, and later asks to delete it. What does each of those requests promise the client, and what does the client get back?

  • posting a long address returns a short code, the long address and the short address, and posting it again returns the same link
  • opening a short address sends the visitor on to the original address
  • deleting removes the link, and asking to delete an unknown link still gets a clear answer
p-whywhy

Who calls this service, and what would those callers lose if it went down or started giving different answers for the same link?

  • other programs, scripts and people clicking links rely on it
  • a short link shared in a post or printed somewhere has to keep working for as long as people expect
  • a changed or missing answer breaks everyone who stored or repeated the short address
p-howhow

The service may restart at any time, and more than one copy of it may run at once. Where would you keep the short codes and their long addresses so they are not lost, and why?

  • keep them outside the running program, in a database or file, so a restart does not wipe them
  • a memory-only store works for a quick try but loses every link on restart
  • copies running side by side must all see the same data, so the store has to be shared
  • the store must find a link by its code quickly

Stage 0 · understand the problem

You will build a copy of the Unix cut tool, a small command that picks chosen columns out of lines of text. It reads a file or whatever arrives through standard input, and writes only the chosen parts of each line to standard output. The selection looks easy, but deciding exactly where one field ends and the next begins is the hard part, and the edge cases such as empty fields, repeated delimiters and lines with no delimiter all have fixed answers. The tool also has to behave like a good Unix filter: it must handle input of any size, keep errors out of the data stream, and report success or failure through its exit status. Matching the real tool's output is how you check your understanding, not the goal in itself.

p-whatwhat

Your tool takes lines of text, a delimiter and a list of field positions. What goes in, what comes out, and what exactly is a field here?

  • input is lines from a named file or from standard input
  • output is only the chosen fields of each line, written to standard output
  • a field is the text between delimiters, identified by its position in the line
  • the delimiter is a single character, with a tab as the default
p-whywhy

Why does a tool this small exist at all, when a spreadsheet can also pull out columns? Where would you expect people to use it?

  • quick column extraction from data exports and logs, without opening a spreadsheet
  • used inside scripts, where the output feeds the next command
  • works on files too big for a spreadsheet, or on a live stream
  • small tools that do one job are meant to be chained together
p-howhow

A friend has a log file far bigger than memory, and another input arrives through a pipe. What is your first idea for handling either one?

  • read and process one line at a time instead of loading everything
  • a pipe has no known length, so the program can't load it all first either
  • write each result out as soon as it is ready

Stage 0 · understand the problem

You build a command-line tool that reads lines of text and prints them in sorted order, much like the Unix sort tool. It takes a file name or standard input and writes the sorted lines to standard output, and later it can also remove repeated lines, let the user pick a sorting method, or shuffle the lines while keeping identical ones together. What makes it harder than it looks is that 'sorted' depends on a rule you must choose, since byte order and a language's alphabetical order give different results for the same text. The simplest approach works on small files but slows down quickly as the input grows, and it fails when the input is larger than memory. A correct tool also has to handle edge cases such as empty files, repeated lines and input that is already sorted.

A teammate says a sort is correct as long as its output is in order. Is that enough? What else must the output keep from the input?

  • the output must be a rearrangement of the input
  • no line may be lost or invented
  • each line must appear as many times as it did in the input, unless duplicates are removed
  • order is defined by a comparison rule, so that rule must be stated
p-whywhy

Why does a small tool like this exist when a spreadsheet or database could sort the same data? Think about where it sits in a chain of commands.

  • it reads a stream and fits between other commands in a pipeline
  • scripts often sort first so that other tools such as uniq or join can work
  • it handles files too big or too many for a spreadsheet
p-howhow

What is the simplest way you could sort the lines of a file, and what happens to it when the file grows much larger? Explain in plain words.

  • repeatedly compare and swap neighbours, or pick the smallest remaining line again and again
  • the work grows much faster than the number of lines
  • the whole file must fit in memory at once

Stage 0 · understand the problem

You build a program that prints the lines of some text that match a pattern, the way the Unix grep tool does. The pattern arrives as an argument, along with either files, a folder tree or text piped in from another program. Matching lines go out unchanged to standard output, and an exit code tells the caller whether any line matched at all. The line is the unit: each one either matches or it doesn't, and a script can act on the result without reading any output. What makes it harder than it looks is that the pattern is a small language of its own, with special symbols and rules about what binds to what, and it must be read exactly right before any line is tested. The tool also has to cope with input too big to hold in memory and with pipes that never end.

  • The exit code reports whether any line matched

Stage 0 · understand the problem

You will build a command line spell checker that reads a word list once and saves a compact summary of it to a file. Later runs load that file and report which words typed on the command line are probably misspelt. The summary is much smaller than the list, so it must answer membership questions without holding every word. p-whatwhat

  • Input is one or more words, checked against the word list the tool was built from
  • Output is a list of words flagged as probably misspelt, not a verdict on each word
  • A flagged word is certainly absent from the list, but an unflagged word is only probably right
  • A word that passes can still be misspelt, so the answer is a likelihood
p-whywhy

Why would anyone keep only a compact summary of a word list rather than the list itself? Think about where such a checker runs, and what other software needs the same trick.

  • Storage and memory are limited on small or old devices
  • A full list is slow to load and search on such devices
  • The same trade appears in databases, caches and web crawlers that must skip costly lookups

p-howhow

Suppose you had to check words against a big word list with no special structure. What is the simplest approach, and what goes wrong as the list grows or the device has little memory?

  • Store every word in full and look each typed word up in the stored list
  • The answers are exact, but the space needed grows with the total length of all the words
  • Each lookup gets slower as the list grows, unless the list is sorted and searched cleverly
  • On a small device the full list may not fit at all

Stage 0 · understand the problem

You build Bitcask, a key-value store made of a small library that holds the data and a command-line tool on top that sets, gets and deletes keys and can tidy up old data. Keys and values go in from the command line, and a get prints the latest value stored for that key, or a not-found reply if the key is missing or was deleted. The store keeps its data in a folder of files, and each command runs as a new process, so anything that must survive has to be on disk before the process exits. The hard part is that nothing is overwritten: every change is added to the end of a log, so old values pile up, and a delete is itself a record that must still count after a restart. Finding the latest value quickly means keeping an index of where each key sits, and that index has to be rebuilt from the files every time the store starts, while a crash that stops a write halfway must not spoil the rest of the data.

  • a key holds one value at a time, so a newer set replaces the older one
  • the stored data survives the end of the run that wrote it

Each request arrives over HTTP and is identified by the client that sent it, and the response is either the page's text or a refusal that tells the client to slow down. The core rule is that each client gets its own allowance over time, so one heavy caller is slowed down without slowing everyone else. What makes it harder than it looks is that the count must stay correct across many requests and clients, must survive between requests, and must still be right when requests overlap, and measuring time accurately is awkward on its own.

p-whatwhat

A client sends a request to the protected endpoint and sometimes gets back a refusal. What does the service take in and give back, and what does the limit promise each client?

  • a request arrives over HTTP and the response is either the normal text or a refusal
  • the open endpoint always answers, while the protected one may refuse
  • the promise is per client: each caller gets its own allowance over time, not a shared total for the whole service
p-whywhy

A team runs a public API, and one customer's script sends thousands of requests a minute and slows the service for everyone. Why would the team limit each client, and who relies on that limit?

  • one heavy caller should not use up capacity that other callers need
  • a limit protects against accidents, such as a runaway retry loop, and against deliberate floods
  • the well-behaved callers and the service's own health depend on the limit holding
p-howhow

Each client's count has to be remembered between requests. Where would you keep it, and what could go wrong if two requests from the same client arrive at the same moment?

  • the counts must live somewhere that outlasts a single request, such as memory in the process or a shared store
  • two requests can read the same count before either writes its update, so one update is lost
  • the check and the update have to happen as one step, or a request can slip past the limit

s2-q1Asks about · The token bucket: capacity, refill and bursts

A client sends one request every 0.9 seconds to a bucket that refills one token a second, and it is refused for good after its first burst. Why does that happen, and what should the bucket do with the time that doesn't yet make a whole token?

  • the refill is computed from the time elapsed since the last update
  • a partial token must be kept, not thrown away
  • the last-update time should move only by the time that was actually converted into tokens
  • the capacity still caps how many tokens can be saved

s6

Distributed rate limiting

manual

Needs two instances and a shared store. The sandbox runs one copy at a time and has no store server.

s6-q7Asks about · Shared state across servers, and atomic updates

Two instances receive requests from the same client at the same moment, and each reads the count, adds one and writes it back. What goes wrong, and how do you stop it?

  • both read the same value and one update is lost
  • extra requests get through the limit
  • the read and the update must happen as one atomic step inside the store
  • an atomic increment, a transaction or a script run by the store does this
s6-q8Asks about · Time and clocks: wall time, elapsed time and skew

Two instances have wall clocks a second apart, and a client's requests arrive right at a window boundary. Each instance decides which window a request is in by its own clock. What goes wrong, and what would you change?

  • wall clocks differ between machines, so instances can disagree about the window
  • requests near a boundary can be counted in different windows
  • the window should be decided from one shared time source, such as the store
  • the same time source must be used by every instance
